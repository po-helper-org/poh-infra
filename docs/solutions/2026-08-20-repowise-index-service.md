# Сервис постоянного индекса кода для агентов

## Ситуация

Агентам контура при каждой задаче нечего было читать, кроме клона репозитория целиком: постоянного индекса кода не было. Появился сервис на открытом пакете Repowise: два MCP-эндпоинта, веб-админка, прокси и индексатор. За индексатором — клоны всех репозиториев организации, поэтому разграничение доступа стало главным вопросом дизайна.

## Причина

Спайк перед интеграцией вскрыл четыре свойства пакета, без обхода которых сервис не поднимался: у `repowise mcp` в 0.36.0 нет ключа `--host` (слушает только loopback, по сети недостижим); `git` отсутствует в базовом образе `python:3.11-slim`, без него `doctor` отвечает `Not a git repo`; имя `REPOWISE_HOST` занято пакетом под адрес сокета; у `repowise serve` свой guard — не-loopback без ключа даёт `403`.

## Решение

- Версия пинится на `0.44.0`, адрес привязки задаётся явным ключом `--host` на все интерфейсы; `git` ставится в образ плюс `safe.directory` — контейнер работает от root, клоны чужие. Домен вынесен в `REPOWISE_PUBLIC_HOST`, поверх basic_auth задан `REPOWISE_API_KEY`.
- Граница доступа проходит по сети, а не по соглашению: порты эндпоинтов и админки не публикуются вовсе, контуру виден один прокси, и тот требует токен. Пустой токен в конфигурации даёт `503`, а не открытый доступ.
- Прокси не разбирает семантику инструментов, только конверт JSON-RPC: имена и сигнатуры у пакета меняются между версиями. Служебные методы MCP (рукопожатие, перечень инструментов) не идут в журнал — иначе шум на каждый прогон и сбитый счётчик ходов.
- Индексатор удаляет секреты (`.env`, `*.pem`, `secrets/`) из рабочих копий до индексации, а не полагается на исключения: ключ, попавший в индекс, оттуда уже не вынуть — он разойдётся по страницам и векторному индексу.
- Структурная индексация отделена от генерации описаний моделью — неудача генерации оставляет работоспособный индекс. Отказ одного workspace не останавливает цикл: молчащий индексатор хуже отставающего.

## Как проверить

35 тестов без сети — контракты прокси и индексатора. Сквозной прогон compose из 16 проверок: отказы `401/400/503` по токенам, сессиям и workspace, `initialize` и `tools/call get_overview` через прокси, транскрипт диалога со свежестью индекса и без токена внутри.

## Уроки

Сквозной прогон на workspace из девяти репозиториев вскрыл шесть дефектов; пять из них на одном репозитории не всплывают вовсе — проверять сервис на самом широком workspace, какие есть. PR ушёл с честным «сквозной прогон не выполнен» (не поднялся Docker-демон) и списком непроверенного; прогон доделали сразу после мержа, и именно он нашёл дефекты.
