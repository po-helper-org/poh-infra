# Поле kind в схеме MCP-инструмента роняло прогон агента разработки

## Ситуация

Прогон агента разработки падал на первом же ходу с `TypeError: Field 'kind' of class 'MCPGetDeadCodeAction' overrides symbol of same name in a parent class`. Опаснее самого отказа его вид: контейнер выходил с нулевым кодом и не трогал ни одного файла. В отчёте значилось «агент не изменил ни одного файла — открывать нечего», снаружи это неотличимо от исправной работы.

## Причина

Фреймворк агента (OpenHands) строит на каждый MCP-инструмент свой класс действия, и имя `kind` у него занято под тип события. Два инструмента индекса (`get_dead_code` и `search_codebase`) объявляли в схеме собственное поле с этим именем — коллизия.

## Решение

Прокси переименовывает поле (kind → kind_) только для сессий агента разработки — их узнают по префиксу имени сессии; вызов с переименованным полем переводит обратно, сам сервис о подмене не знает. Инструмент не выбрасывался: без `search_codebase` агент теряет главный способ искать по индексу, то есть смысл интеграции. Правило заведено по имени поля, а не по имени инструмента: инструменты переименуют с версией пакета, причина останется прежней; остальным клиентам перечень достаётся нетронутым.

## Как проверить

Тесты прокси на зарезервированное поле (`repowise/tests/test_proxy_reserved.py`): схема с kind доезжает до агента переименованной, вызов доходит до сервиса с исходным именем.

## Уроки

Схема стороннего MCP-инструмента не обязана быть совместимой с конкретным клиентом — коллизии имён ловит та сторона, которая их связывает. И снова: нулевой код выхода у упавшего прогона — худший вид отказа, см. кейс о молчаливом no-op.
