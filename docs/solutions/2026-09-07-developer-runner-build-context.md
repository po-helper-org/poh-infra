# Стадия разработки уехала в свой репозиторий — и за ней надо следить отдельно

## Ситуация

Стадию «Разработка» контура перенесли в отдельный репозиторий. Теперь `openhands-runner` собирается из `DEVELOPER_AGENT_CONTEXT` вместо `ISSUE_AGENT_CONTEXT`. Попутно выяснилось: переменная `DEVELOP_RUNNER_IMAGE`, по имени которой воркер запускает контейнер прогона, не была объявлена нигде — compose читал её вслепую.

## Причина

Корневой контекст сборки с выбором файла по ключу `dockerfile:` одним значением обслуживает несколько сервисов. Вторая переменная на тот же репозиторий завела бы два адреса, обязанных совпадать, а сверить их было бы нечем. Опасность разъезда проявляется молча: сборка проходит, а прогон падает на отсутствующем образе уже внутри задачи.

## Решение

Одна переменная контекста на репозиторий; плавающий `#main` здесь принят осознанно — образ не участвует в replay durable-воркфлоу Temporal, пересборка есть действие оператора. Код стадии, участвующий в replay, приезжает отдельно, пакетом с пином по тегу. Найденную переменную объявили в env-примере и справочнике конфигурации; упоминания контекста обновлены сразу в четырёх документах.

## Как проверить

Сборка тем же корневым контекстом в CI нового репозитория: uid раннера и мажор Node в образе совпадают с объявленными, агент стартует. Локально: YAML compose валиден, старая переменная осталась у своих сервисов.

## Уроки

Каждый отпочковавшийся репозиторий тянет за собой хвост из мест, где упомянут контекст сборки: справочник конфигурации, релизная заметка для DevOps и безопасности (сборок из git стало четыре, сеть сборки должна доставать ещё один репозиторий), правило пиннинга, статус-заметка с отдельной командой пересборки. Обновлять все: половина упоминаний — та же молчаливая деградация, отложенная во времени.
