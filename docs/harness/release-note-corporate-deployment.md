# Релизная заметка: харнесс контура автоматизации Issue → PR
## Материал для рассмотрения DevOps и СБ перед развёртыванием в корпоративной инфраструктуре

> Статус: черновик для ревью. Все факты ниже сверены с текущим содержимым
> репозитория (`harness/docker-compose.yml`, `harness/.env.example`,
> `harness/Caddyfile`, `harness/register-app.html`, `harness/host/`) и с
> опытом эксплуатации демонстрационного стенда. Раздел
> [«Открытые вопросы»](#8-открытые-вопросы-к-devops-и-сб) перечисляет то, что
> без решения инфраструктурного департамента не имеет ответа.

---

## 1. Что это

Харнесс — один Docker Compose стек, который связывает три независимых
сервиса в замкнутый производственный цикл: заявка (GitHub Issue) → анализ →
разработка → Pull Request → ревью → доклад о результате обратно в задачу.

```
GitHub ──webhook──▶ caddy ──/issue/*──▶ issue-webhook ──▶ Temporal ──▶ issue-worker
                      │                                                     │
                      │                                          workflow_dispatch
                      │                                                     ▼
                      └──/pr/*──▶ pr-ingress ─▶ pr-worker         OpenHands (Actions)
                                                    │                       │
                                                    └──── /agent-event ◀────┘
```

- **Issue-Agent** — принимает вебхуки GitHub, ведёт заявку по стадиям (триаж →
  аналитика → декомпозиция → передача в разработку) как воркфлоу Temporal.
- **Temporal** — движок долгоживущих процессов (собственные `postgres` +
  `temporal` + `temporal-ui`), состояние заявки хранится как история событий.
- **PR-Agent** (опционален, включается профилем `pr`) — автоматическое ревью
  открытых Pull Request.
- **Caddy** — единственная публичная точка входа, разводит один домен на
  четыре внутренних адреса.

Полная архитектура и пошаговый цикл — [`harness/README.md`](../../harness/README.md).
Исходники Issue-Agent и PR-Agent — отдельные репозитории
(`po-helper-org/poh-issue-agents`, `po-helper-org/poh-pr-agents`), харнесс их
не копирует, а собирает `docker build` прямо из git на этапе `docker compose
up --build` (см. [§7](#7-используемые-зависимости) про связанный риск цепочки
поставки).

## 2. Компоненты стека

| Сервис | Образ / сборка | Роль | Обязателен |
|---|---|---|---|
| `postgres` | `postgres:16` | БД Temporal | да |
| `temporal` | `temporalio/auto-setup:1.24` | движок воркфлоу | да |
| `temporal-ui` | `temporalio/ui:2.31.2` | консоль оператора | да |
| `issue-webhook` | сборка из `poh-issue-agents` (`webhook/Dockerfile`) | приём вебхуков, HTTP-фасад | да |
| `issue-worker` | сборка из `poh-issue-agents` (`worker/Dockerfile`) | исполнение воркфлоу, вызовы модели | да |
| `openhands-runner` | сборка из `poh-issue-agents` (`openhands/Dockerfile`) | образ для одноразового контейнера агента разработки; сам не «служит» | да (как образ) |
| `caddy` | `caddy:2-alpine` | реверс-прокси, единственный публичный вход | да |
| `pr-agent-base` | сборка из `qodo-ai/pr-agent` (апстрим, внешний репозиторий) | базовый образ ревью PR | только профиль `pr` |
| `pr-ingress` / `pr-worker` / `pr-sweeper` | сборка из `poh-pr-agents` (`self-hosted/`) | приём вебхуков PR, очередь ревью, доретрай пропущенных | только профиль `pr` |

Источник правды по составу — [`harness/docker-compose.yml`](../../harness/docker-compose.yml).

## 3. Конфигурация

Один файл `.env` на весь стек, шаблон с комментариями —
[`harness/.env.example`](../../harness/.env.example), построчный справочник —
[`docs/harness/configuration.md`](configuration.md). Ниже — сводка того, что
обязательно и почему отсутствие переменной не выглядит как явная ошибка.

| Группа | Переменные | Поведение при пропуске |
|---|---|---|
| Репозитории под контуром | `WATCHED_REPOS` (обязательна) | `docker compose up` падает сразу, на подстановке — до сборки образов дело не доходит |
| GitHub App «Issue-Agent» | `ISSUE_APP_ID`, `ISSUE_APP_PRIVATE_KEY_B64`, `ISSUE_APP_WEBHOOK_SECRET` (секрет обязателен) | без App — работает по `GH_TOKEN` (см. [§8](#8-открытые-вопросы-к-devops-и-сб)) |
| GitHub App «PR-Agent» | `PR_APP_ID`, `PR_APP_PRIVATE_KEY_B64`, `PR_APP_WEBHOOK_SECRET` | без них профиль `pr` не поднимается вовсе (guard на старте контейнера) |
| Замок контура | `AGENT_EVENT_SECRET` (обязательна) | пусто → эндпоинт `/agent-event` отвечает 503; всё остальное продолжает работать, задачи «зависают» в `in-development` без единой ошибки — самая дорогая по времени диагностики ошибка конфигурации |
| Модель | `ZAI_API_KEY` (обязательна), `ZAI_BASE_URL`, `MODEL_GATE`, `MODEL_CLASSIFY`, `PR_AGENT_MODEL` | без ключа сборка и обвязка поднимаются, вызовы модели падают в рантайме |
| Автономность цикла | `DRY_RUN`, `DEVELOP_ENABLED`, `RESEARCH_AUTOSTART`, `DEVELOP_AUTOSTART`, `DEVELOP_MODE`, `AGENT_TRIGGER_ALLOWLIST` | по умолчанию `DRY_RUN=1` — ни одной записи в GitHub, безопасно для первого прогона |
| Инфраструктура | `POSTGRES_PASSWORD` (обязательна), `HARNESS_PORT`, `HARNESS_HOST`, `PUBLIC_URL`, `TEMPORAL_UI_PORT` | без пароля БД — падение на старте `postgres` |
| Наблюдаемость | `SENTRY_DSN`, `SENTRY_ORG`, `SENTRY_ENVIRONMENT` | пусто = выключено, это же и процедура отката |

**Секреты, которые сознательно не в `.env`:** учётка Temporal UI
(`TEMPORAL_UI_USER` / `TEMPORAL_UI_PASSWORD_HASH`) хранится отдельным файлом
вне рабочей копии (`/etc/poh-harness/temporal-ui-auth.env` на текущем
демо-стенде, `harness/caddy.env` локально) — общий `.env` может быть
перезаписан панелью деплоя, и учётка не должна пропадать вместе с ним.
Подробности и формат — [configuration.md, «Что не в `.env` на стенде»](configuration.md#что-не-в-env-на-стенде).

## 4. Инструкция развёртывания

Кратко (полная версия, шаг за шагом, с граблями — [`harness/DOKPLOY.md`](../../harness/DOKPLOY.md)
для постоянного стенда через панель деплоя, [`harness/LOCAL.md`](../../harness/LOCAL.md)
для локального прогона):

1. **Поднять хост** с Docker Engine + Compose v2 (директива `build` — плагину
   `stack` она недоступна, нужен именно `docker-compose`).
2. **Скопировать конфиг:** `cp harness/.env.example harness/.env`, заполнить
   обязательные переменные (см. [§3](#3-конфигурация)).
3. **Завести домен**, направить его на сервис `caddy` (порт 80 внутри), задать
   `HARNESS_HOST` и `PUBLIC_URL` этим же адресом.
4. **Завести два GitHub App** — форма `harness/register-app.html` собирает
   манифест прав и событий (см. [§8](#8-открытые-вопросы-к-devops-и-сб) —
   точный набор прав); PR-Agent регистрируется отдельно, по документации
   апстрима `qodo-ai/pr-agent`.
5. **Прописать секреты в каждом репозитории** из `WATCHED_REPOS`:
   `ISSUE_AGENT_URL`, `AGENT_EVENT_SECRET`, ключ модели.
6. **Поднять стек:** `docker compose up -d --build` (профиль `pr` — отдельным
   флагом `--profile pr`, если PR-Agent разворачивается как сервис, а не
   остаётся CI-шагом целевого репозитория).
7. **Проверить по цепочке**, каждый шаг ловит ровно один обрыв:
   ```bash
   D=https://<домен>
   curl -fsS "$D/health"                                                    # харнесс жив
   curl -s -o /dev/null -w '%{http_code}\n' -X POST "$D/issue/webhook"      # 401/422 = приём живой
   curl -s -o /dev/null -w '%{http_code}\n' -X POST "$D/issue/agent-event"  # 401 = секрет задан, 503 = не задан
   curl -s -o /dev/null -w '%{http_code}\n' "$D/"                            # 401 = вход в UI закрыт паролем
   ```

**Автодеплоя на изменение кода агентов нет.** Образы собираются из
git-контекста (`ISSUE_AGENT_CONTEXT` / `PR_AGENT_CONTEXT`) в момент `docker
compose build`; выкладка новой версии — пересборка с пином на конкретный
коммит, вручную или через пайплайн, который заведёт DevOps (см.
[§8](#8-открытые-вопросы-к-devops-и-сб)).

## 5. Сетевые доступы

### Входящие (обязательные)

| Источник | Куда | Порт/протокол | Назначение |
|---|---|---|---|
| GitHub (вебхуки) | `caddy` | 80/443 → `/issue/webhook`, `/pr/webhook` | события Issues, PR, push |
| Внешние агенты (OpenHands в Actions, PR-Agent) | `caddy` | 80/443 → `/issue/agent-event` | доклад о результате шага, подписан `AGENT_EVENT_SECRET` |
| Оператор (человек) | `caddy` | 80/443 → `/` | Temporal UI, basic-auth |
| Мониторинг | `caddy` | 80/443 → `/health` | проверка живости |

Публичным должен быть **только** порт `caddy` (80, и 443 при наличии TLS).
Всё остальное — `postgres` (5432), `temporal` (7233), прямой порт
`temporal-ui` (8233 в текущей конфигурации) — должно слушать исключительно
loopback/внутреннюю сеть. В `docker-compose.yml` `temporal-ui` уже объявлен на
`127.0.0.1:${TEMPORAL_UI_PORT}`; `postgres` и `temporal` не публикуют портов
наружу вовсе (`expose`, не `ports`) — это должно быть подтверждено на целевом
хосте отдельно от Compose-файла, если периметр организован иначе (NAT,
security group и т.п.).

Референсный паттерн изоляции от соседних сервисов на том же хосте —
[`harness/host/poh-harness-isolation.sh`](../../harness/host/poh-harness-isolation.sh)
(правила `iptables`/`DOCKER-USER`, закрывающие RFC1918 наружу из подсети
контура и порты хоста от контейнеров контура). Написан для конкретного
случая — общий хост с чужим стеком; в выделенном корпоративном сегменте
эквивалент, вероятно, обеспечивается сетевой сегментацией средствами
инфраструктуры, а не этим скриптом.

### Исходящие

| Куда | Зачем | Обязательность |
|---|---|---|
| `github.com`, `api.github.com` | вебхуки, API-вызовы GitHub App (метки, комментарии, PR), клонирование исходников агентов и `qodo-ai/pr-agent` при сборке образов | обязательно |
| `api.z.ai` (пути `/api/coding/paas/v4` и `/api/anthropic`) | вызовы модели — и из Python-кода агентов, и из встроенного в образ CLI (см. [§7](#7-используемые-зависимости)) | обязательно |
| Sentry (`SENTRY_DSN`, при заполнении) | доставка ошибок | опционально, выключено по умолчанию |
| Реестры пакетов при сборке образов (Docker Hub/GHCR за базовыми `FROM`, `registry.npmjs.org`, релизы GitHub CLI и Claude Code) | сборка `issue-webhook`/`issue-worker`/`openhands-runner`/`pr-*` | только во время `docker compose build`, не в рантайме |
| ACME `acme-v02.api.letsencrypt.org` (если TLS выпускается автоматически, как на демо-стенде через Traefik) | выпуск сертификата | зависит от выбранной схемы TLS в корп. инфраструктуре, см. [§8](#8-открытые-вопросы-к-devops-и-сб) |

## 6. Вычислительные ресурсы

Цифры ниже — наблюдения с демонстрационного стенда (внешняя VM, не
корпоративное железо), а не гарантированный SLA. Профиль нагрузки
(параллельность заявок, размер репозиториев) в корпоративном контуре не
определён — раздел [§8](#8-открытые-вопросы-к-devops-и-сб) просит зафиксировать
ожидаемую нагрузку до расчёта лимитов.

| Что | Наблюдение | Источник |
|---|---|---|
| Сборка образов | нужно ~4 ГБ ОЗУ билдеру; в образ воркера ставятся Node.js, GitHub CLI и Claude Code (~1.6 ГБ слоями) | `harness/DOKPLOY.md` |
| Контейнер `issue-worker` в покое | ~286 МБ RSS | замер на демо-стенде |
| Один вызов `claude -p` (используется частью стадий агента) | ~356 МБ RSS на вызов, то есть дороже самого контейнера воркера | замер на демо-стенде, 2026-08-19 |
| Демо-стенд целиком | ~8 ГБ ОЗУ хоста хватало впритык; при нескольких одновременных `claude -p` плюс контейнер агента разработки сборка переставала укладываться в 10 минут | наблюдение с демо-стенда |
| Диск | размер образа воркера ~1.6+ ГБ (Node.js + GitHub CLI + Claude Code), плюс стандартные образы Temporal/Postgres/Caddy; рост `pgdata` от объёма истории воркфлоу не измерялся | — |

**Рекомендация:** прежде чем фиксировать лимиты CPU/RAM в корпоративной
инфраструктуре — прогнать нагрузочный сценарий на целевом классе инстансов;
цифры демо-стенда систематически занижены (общий хост, к тому же делит
память с посторонним сервисом).

## 7. Используемые зависимости

**Базовые образы:** `postgres:16`, `temporalio/auto-setup:1.24`,
`temporalio/ui:2.31.2`, `caddy:2-alpine` — версии зафиксированы в
`docker-compose.yml`.

**Собственные образы собираются из исходников на этапе `docker compose
build`**, а не берутся готовыми из реестра:
`ISSUE_AGENT_CONTEXT=https://github.com/po-helper-org/poh-issue-agents.git#main`,
аналогично для `PR_AGENT_CONTEXT` и апстрима `qodo-ai/pr-agent`. Это значит,
что **сеть сборки должна иметь доступ к GitHub в момент `build`**, и что
цепочка поставки включает три внешних git-репозитория (два своих, один
чужой — `qodo-ai/pr-agent`), а не только образы из корпоративного реестра.
Для корпоративного контура это, вероятно, потребует либо зеркалирования
источников во внутренний Git, либо явного исключения в политике egress на
время сборки — решение за DevOps/СБ.

**Внутри образа `issue-worker` установлены:** Node.js, GitHub CLI, Claude
Code CLI. Часть стадий агента (см. `BFT_DIRECT_STAGES`) вызывает модель
напрямую по HTTP, часть — через `claude -p`.

**Провайдер модели — z.ai, не Anthropic**, несмотря на то что в контуре
используется CLI с именем «Claude Code»: и Python-код, и CLI обращаются к
`api.z.ai` (`ZAI_API_KEY`, эндпоинты `/api/coding/paas/v4` и `/api/anthropic`
соответственно) и используют модели линейки GLM (`glm-4.6`, `glm-4.5-air`).
Собственных ключей или трафика к `api.anthropic.com` в контуре нет. Это
существенно для оценки СБ — юрисдикция и статус провайдера данных,
уходящих в промпты (код репозитория, содержимое Issue), другие, чем при
прямой интеграции с Anthropic.

**GitHub Apps:** два независимых приложения (см. [§8](#8-открытые-вопросы-к-devops-и-сб)
про точный набор прав) — разведены по правам намеренно, единый ключ означал
бы, что утечка одного открывает разом и бэклог, и код репозитория.

## 8. Права доступа

### GitHub App «Issue-Agent»

Манифест собирается формой [`harness/register-app.html`](../../harness/register-app.html):

| Право | Уровень |
|---|---|
| `issues` | write (метки, комментарии, sub-issues) |
| `pull_requests` | write (PR от агента разработки) |
| `contents` | write (ветки аналитики и разработки) |
| `actions` | write (диспатч прогона в режиме `DEVELOP_MODE=dispatch`) |
| `metadata` | read |

События: `issues`, `issue_comment`, `label`, `pull_request`, `push`,
`sub_issues`.

**Запасной путь без App — `GH_TOKEN` (PAT).** `github_client` предпочитает
токен, если он задан, и тогда переменные `ISSUE_APP_*` можно оставить
пустыми. В этом режиме все действия в GitHub идут **от имени человека —
владельца токена**, а не от имени бота; воркер пишет об этом
предупреждение в лог. Для корпоративного контура это отдельный вопрос
политики учётных записей — держать сервисный PAT или обязать App.

### GitHub App «PR-Agent»

Приложение регистрируется отдельно от Issue-Agent (форма в репозитории его
не собирает) по документации апстрима `qodo-ai/pr-agent`: типичный набор —
чтение содержимого и метаданных PR, запись комментариев/ревью, чтение
проверок (checks). Точный манифест не завезён в этот репозиторий — если
PR-Agent разворачивается как отдельный сервис (профиль `pr`), манифест нужно
свести отдельно перед регистрацией.

### Внутренний секрет каналов — `AGENT_EVENT_SECRET`

Симметричная строка, одна на обе стороны канала `/agent-event`: ею же
подписывают доклад PR-Agent и прогон OpenHands в Actions целевого
репозитория. Хранится и в `.env` харнесса, и секретом в каждом репозитории
из `WATCHED_REPOS`. Ротация требует одновременной замены в обоих местах.

### Повышенная привилегия: доступ `issue-worker` к Docker-сокету хоста

`issue-worker` монтирует `/var/run/docker.sock`, чтобы поднимать
одноразовый контейнер агента разработки для исполнения кода из
обрабатываемого репозитория. **Это равносильно доступу уровня root на
хосте** — держатель сокета может поднять произвольный контейнер с любым
монтированием. Компенсирующий контроль, заложенный в архитектуру: сам
сгенерированный код исполняется не в `issue-worker`, а в отдельном
одноразовом контейнере, у которого нет ни GitHub-токена, ни доступа к
истории Temporal, и который живёт минуты. Проектное решение принято
осознанно (см. комментарий в `docker-compose.yml` у сервиса `issue-worker`),
но остаётся фактом, который нужно явно предъявить СБ, а не обнаружить
постфактум — это ровно тот класс риска, ради которого пишется эта заметка.

### Temporal UI

Закрыт basic-auth на уровне `caddy` (учётка вне общего `.env`, см.
[§3](#3-конфигурация)). Прямой порт (`TEMPORAL_UI_PORT`) без пароля, но
привязан к loopback — доступ только с самого хоста либо через SSH-туннель
оператора.

## 9. Известные ограничения (чтобы не стали сюрпризом после выкладки)

- **Нет автодеплоя кода агентов** — выкладка новой версии Issue-Agent/PR-Agent
  требует пересборки образа с явным пином git-коммита; процесс CI/CD для
  этого в корпоративной инфраструктуре ещё не определён.
- **Кэш сборки BuildKit кэширует git-клон по URL** — пересборка после нового
  коммита в ту же ветку (`#main`) может молча взять прежний код; на
  постоянной инсталляции для этого нужен пин на полный SHA или `--no-cache`.
- **Долгие процессы Temporal чувствительны к моменту рестарта воркера** —
  выкладка «прямо сейчас» может уронить идущие процессы (`Nondeterminism
  error`) или потерять heartbeat долгой активности; подробности —
  [`harness/STATUS.md`](../../harness/STATUS.md#чем-опасна-выкладка-на-живой-стенд).
- **PR-Agent как отдельный сервис нигде ещё не эксплуатировался** — на
  единственном прогнанном сценарии ревью выполнялось CI-шагом в Actions
  целевого репозитория, а не профилем `pr` этого стека.
- **`DRY_RUN` — пустая строка означает боевой режим, `0` не выключает сухой
  прогон** — частый источник путаницы при первом запуске.

## 10. Открытые вопросы к DevOps и СБ

1. **Модель угроз для доступа к Docker-сокету хоста** ([§8](#8-права-доступа))
   — приемлема ли эта архитектура для корпоративного хоста, и если нет —
   какая изоляция (отдельная VM/нода для `issue-worker`, gVisor/Kata,
   что-то ещё) заменит текущий компенсирующий контроль.
2. **Провайдер модели — z.ai (GLM)** ([§7](#7-используемые-зависимости)) —
   согласован ли вывод кода репозиториев и текста Issue во внешний сервис
   этого провайдера; если требуется другой провайдер — что меняется в
   `ZAI_BASE_URL`/`ZAI_API_KEY` и совместим ли он с форматом вызовов Claude
   Code CLI (`/api/anthropic`-путь).
3. **Egress к GitHub в момент сборки образов** ([§7](#7-используемые-зависимости))
   — допустим ли `docker build` с git-контекстом из публичного GitHub
   (включая сторонний `qodo-ai/pr-agent`), или нужно зеркалирование во
   внутренний реестр/Git перед публикацией.
4. **Схема TLS/сертификатов** — демо-стенд использует автоматический выпуск
   Let's Encrypt через Traefik; какая схема принята в корпоративной
   инфраструктуре (внутренний CA, готовый wildcard-сертификат, свой
   балансировщик перед `caddy`).
5. **Ожидаемая нагрузка** ([§6](#6-вычислительные-ресурсы)) — сколько
   репозиториев и одновременных заявок предполагается обслуживать, чтобы
   зафиксировать лимиты CPU/RAM/диска вместо цифр с демо-стенда.
6. **Учётные записи GitHub App vs `GH_TOKEN`** ([§8](#8-права-доступа)) —
   политика организации по сервисным идентичностям: обязательны ли оба App,
   или для внутренних репозиториев допустим PAT.
7. **Хранение секретов** — текущая схема (`.env` + два файла вне рабочей
   копии для учётки Temporal UI) рассчитана на Dokploy; годится ли она как
   есть или нужна интеграция с корпоративным хранилищем секретов (Vault и
   т.п.).
8. **Ротация `AGENT_EVENT_SECRET` и вебхук-секретов** ([§8](#8-права-доступа))
   — принятая в организации периодичность и процедура, чтобы вписать её в
   регламент эксплуатации контура.
