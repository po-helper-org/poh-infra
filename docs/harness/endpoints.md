# Публичные точки входа

Харнесс наружу отдаёт один HTTP(S)-хост. Внутри него все запросы разбирает
Caddy ([`harness/Caddyfile`](../../harness/Caddyfile)) и раскладывает по
четырём сервисам. Второй домен заводить не нужно и не стоит — адрес вебхука
прописан в двух местах руками (настройки GitHub App и секрет
`ISSUE_AGENT_URL` каждого репозитория), и лишний хост — это ещё одно место,
где конфигурация может незаметно разойтись.

## Карта маршрутов

| Путь | Что за ним | Кто туда ходит | Auth |
|---|---|---|---|
| `/health` | Живость харнесса: 200 `harness ok`, если жив хотя бы прокси | человек, мониторинг | нет |
| `/issue/webhook` | Приём вебхуков GitHub для Issue-Agent | GitHub App «Issue-Agent» | подпись `ISSUE_APP_WEBHOOK_SECRET` |
| `/issue/agent-event` | Приём докладов о PR и ревью от внешних агентов | прогон OpenHands (Actions), PR-Agent | `AGENT_EVENT_SECRET` |
| `/pr/webhook` | Приём вебхуков GitHub для PR-Agent | GitHub App «PR-Agent» | подпись `PR_APP_WEBHOOK_SECRET` |
| всё остальное (корень домена) | Temporal UI | человек-оператор | basic-auth (`TEMPORAL_UI_USER` / `TEMPORAL_UI_PASSWORD_HASH`) |

Порядок в таблице — это и порядок разбора в `Caddyfile`: три конкретных пути
проверяются первыми, всё, что не подошло ни под один, достаётся Temporal UI.

### Почему Temporal UI — не путь, а «всё остальное»

Казалось бы естественным повесить UI на `/temporal/*`, как остальные три
сервиса. Так и было сделано изначально — и страница открывалась пустой белой
без единой ошибки в логах caddy или temporal-ui.

Причина: образ `temporalio/ui:2.31.2` собран как SPA (SvelteKit), и путь
монтирования (`base`) зашит в JS-бандл на этапе сборки как **пустая
строка**. Что бы ни стояло в `TEMPORAL_UI_PUBLIC_PATH`, браузер всё равно
запрашивает ассеты абсолютными путями вида `/_app/immutable/entry/start.…js`
— от корня домена, а не от префикса, под которым открыли страницу.
`TEMPORAL_UI_PUBLIC_PATH` при этом не бесполезен — он двигает *серверные*
API-маршруты самого UI, — но на генерацию ссылок на статику не влияет.

Под `/temporal/*` браузер честно грузил `index.html`, а следующим шагом шёл
за `/_app/...` — Caddy такого маршрута не знал, отвечал общим 404, и
SvelteKit не успевал даже инициализироваться. Единственный рабочий вариант
для этой версии образа — отдать Temporal UI домен целиком. Три остальных
сервиса — обычные JSON-эндпоинты без собственных статических ассетов, им
префикс не мешает вообще.

Если версия `temporalio/ui` в будущем научится честно уважать
`TEMPORAL_UI_PUBLIC_PATH` для сборки ассетов — можно будет вернуть её под
`/temporal/*` и освободить корень. До тех пор корень домена занят под UI.

## Прямой порт Temporal UI

Помимо основного входа, `temporal-ui` слушает `127.0.0.1:${TEMPORAL_UI_PORT:-8233}`
на самом хосте — но **только loopback**, не наружу. Он нужен, чтобы отличить
«UI не работает» от «маршрутизация до UI не работает»: если по прямому порту
UI открывается, а через Caddy — нет, ищи проблему в `Caddyfile`, а не в
самом `temporal-ui`.

Снаружи сервера порт закрыт файрволом, поэтому дойти до него — через
SSH-туннель:

```bash
ssh -L 8233:127.0.0.1:8233 poh-stand
open http://localhost:8233/
```

Прямой порт без basic-auth. Это осознанно: снаружи он и так недостижим, и
второй слой пароля поверх уже закрытого файрволом порта ничего не добавляет.

## Как управлять маршрутами

Все три вещи, которые нужны, чтобы что-то поменять в схеме адресов, лежат
в разных местах — держи их в голове вместе:

| Хочу... | Где менять |
|---|---|
| Добавить/убрать путь, поменять, на какой сервис он проксируется | [`harness/Caddyfile`](../../harness/Caddyfile) |
| Поменять хост, на который отвечает Traefik (снаружи Docker) | переменная `HARNESS_HOST` — метки на сервисе `caddy` в [`docker-compose.yml`](../../harness/docker-compose.yml) |
| Поменять адрес, который видят Issue-Agent/PR-Agent/Temporal UI внутри себя (для CORS, для ссылок в комментариях) | переменная `PUBLIC_URL` |
| Поменять порт харнесса на самом хосте (без Traefik/Dokploy) | переменная `HARNESS_PORT` |
| Поменять учётку Temporal UI | `TEMPORAL_UI_USER` / `TEMPORAL_UI_PASSWORD_HASH` — **не** в общем `.env`, см. [«Отдельный файл для учётки UI»](configuration.md#отдельный-файл-для-учётки-temporal-ui) |

`HARNESS_HOST` и `PUBLIC_URL` — это один и тот же адрес, названный дважды по
двум разным причинам: первый собирает правила Traefik (`Host(...)`), второй
доезжает до сервисов как переменная окружения для CORS и подписи вебхуков.
Разъехавшись, они дают рабочий вход и пустую страницу — CORS браузера режет
запросы, которые страница делает сама к себе.

## HTTPS и сертификат

На entrypoint `websecure` Traefik сам получает сертификат Let's Encrypt по
HTTP-01 (резолвер `letsencrypt`, настроен глобально на уровне Dokploy-Traefik
— в самом харнессе трогать нечего). Единственное условие — домен должен
резолвиться на IP сервера, и метки роутера на сервисе `caddy` должны его
называть (`HARNESS_HOST`).

**Домены вида `*.traefik.me` для боевого HTTPS не годятся.** Это общий
домен-обёртка (не в Public Suffix List), и лимит Let's Encrypt на выпуск
новых сертификатов (50 в неделю) общий на всех, кто им пользуется —
случайные стенды других людей выбирают лимит раньше, чем доходит очередь.
Traefik в этом случае пишет в лог `too many certificates (50) already issued
for "traefik.me"` и продолжает отдавать дефолтный самоподписанный
сертификат. Для постоянного стенда заводи A-запись на собственном домене.

## Проверка, что всё разобрано верно

Порядок не случаен — каждый шаг проверяет ровно одно звено:

```bash
D=https://<домен>

curl -fsS "$D/health"                                                    # 1. харнесс жив
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$D/issue/webhook"      # 2. 401/422 = живой приём, 404 = не тот путь
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$D/issue/agent-event"  # 3. 401 = секрет задан, 503 = AGENT_EVENT_SECRET пуст
curl -s -o /dev/null -w '%{http_code}\n' "$D/"                            # 4. 401 = вход закрыт паролем, 200 без auth = UI открыт всем — чини срочно
```

**503 на шаге 3 — самая дорогая из возможных ошибок конфигурации.** Всё
остальное продолжает работать, задачи доходят до разработки, PR открываются
— и ни одна задача не закрывается, потому что доклад о готовом PR отвергается
на входе. Симптом неотличим от «агент разработки завис», и найти его без
этой проверки можно только по логам `issue-worker`.
