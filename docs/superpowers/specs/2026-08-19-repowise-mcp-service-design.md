# Repowise MCP — сервис контекста для агентов контура

Дата: 2026-08-19
Задачи: [poh-infra#1](https://github.com/po-helper-org/poh-infra/issues/1) — сервис;
[poh-issue-agents#72](https://github.com/po-helper-org/poh-issue-agents/issues/72) — агенты.

## Задача

Агенты контура — Issue, PR, OpenHands — собирают контекст репозитория заново в
каждом прогоне: клон, repomix, чтение файлов. Знание умирает вместе с прогоном.
Repowise держит постоянный индекс (граф, git-история, blame, семантический
поиск, health, risk, dead code) и отдаёт его по MCP.

Шаг Repowise в аналитике запланирован с июля и заблокирован: T5.2 и T5.6 в
`poh-issue-agents/specs/implementation-spec.md`, «Требует решения» в
`docs/ROADMAP.md:139`. Эта работа снимает блокировку.

## Обстановка

`repowise` 0.36.0 покрывает потребность целиком, форк не нужен:
`mcp --transport streamable-http` (MCP по HTTP), `serve` (API и веб-UI),
`workspace add|scan|list|check|metrics` (мультирепо, +2 инструмента MCP),
`init --no-prose` (индекс без модели), `update -w` (инкремент).

В организации Repowise до сих пор существует только как локальный образ MCP
Toolkit `mcp/poh-repowise:latest` для интерактивных сессий — по одному каталогу
за раз, без сервиса.

## Принятые решения

### Р1. Отладка локально, выкладка в контур — отдельной задачей

На стенде `available` ≈ 1.4 ГБ при нулевом swap; первичная индексация не влезет
и заденет соседей (см. `poh-harness-stand`). Весь стек отлаживается локально,
выкладка ставится третьей задачей после того, как решится вопрос с памятью
сервера.

### Р2. Два workspace: `contour` и `product`

Workspace repowise — это один корневой каталог, один default-репозиторий и один
MCP-эндпоинт; два workspace означают два контейнера на разных портах.

Режем по границе вопроса, не команды: `contour` отвечает «как устроены сами
агенты», `product` — «что агенты пишут». Один workspace на всё дал бы шум
(вопрос про целевой репозиторий притягивает ответ про poh-core), workspace на
каждый продукт — N контейнеров и N расписаний индексации при сегодняшнем одном
целевом репозитории.

Правила R1–R9 — в `docs/repowise/workspaces.md` и в теле poh-infra#1. Самое
неочевидное: `.claude/worktrees/**` обязательно в исключениях — в
`poh-issue-agents` лежат worktree-копии его самого, и без этого индекс
утроится, а `search_codebase` начнёт отдавать устаревшие копии как
самостоятельные файлы.

### Р3. Актуальность — индексатором по расписанию

Отдельный сервис в том же compose: `git fetch && reset --hard origin/HEAD` →
`workspace scan -y` → `repowise update -w`. Первичная индексация — тот же
контейнер с флагом bootstrap.

Вебхук из харнесса дал бы свежесть в секунды, но связал бы два контура и добавил
маршрут в настройки GitHub App. Начинаем с расписания; ручка «обнови репозиторий
X» закладывается в прокси, чтобы вебхук включился позже без переписывания.

Устаревший индекс опаснее отсутствующего: агент уверенно ответит про код,
которого больше нет. Возраст индекса обязан быть видимым, runbook — описывать
починку.

### Р4. Проза отдельным шагом после структурного индекса

`init --no-prose` проходит без модели и без трат гарантированно. `generate
--unwritten` идёт следом. Если провайдер не завёлся, на руках рабочий
структурный индекс, а не половина.

### Р5. Транскрипт диалога пишет прокси, не модель

Между repowise и агентами встаёт тонкий сервис: маршрутизирует по workspace,
требует `session` и bearer-токен, журналирует каждый вызов и ответ, рендерит
`repowise-dialog.md`.

Альтернатива — доверить запись модели с guard'ом на пустой файл. Отвергнута: в
контуре уже зафиксирован класс отказов «шаг отработал, успех доложен, артефакта
нет» (`poh-harness-silent-failures`), и транскрипт от модели принадлежит ровно
ему. Прокси даёт одинаковый механизм для `claude -p` и для OpenHands, у которого
хуков нет вовсе.

Журнал в прокси, а не патчем в repowise: пакет внешний и движется, форк пришлось
бы тащить вечно.

Следствие: прокси не делает смысловой выжимки. «Сводку источников» он строит
механически, а выжимку для sa-helper делает стадия аналитики при чтении файла.

### Р6. Внутренний контур — сетью, не соглашением

MCP-порты не публикуются на хост, Traefik про них не знает. В общей с харнессом
сети виден только прокси, и он требует bearer-токен. Веб-админка — свой домен,
`basic_auth` на caddy, хэш отдельным файлом вне `.env` с удвоенными долларами
(панель Dokploy перетирает `.env`; тот же приём и та же ловушка, что у Temporal
UI). Без переменных учётки caddy не поднимается: упавший вход лучше молча
открытого.

Пароль не переиспользуется с Temporal UI — внутри лежат клоны всех репозиториев
организации и ключ модели, доступ к админке равен доступу к коду.

### Р7. Артефакт забирает воркер, не раннер

Для OpenHands `repowise-dialog.md` тянет воркер у прокси после прогона. Пиши его
раннер — диалог терялся бы при падении раннера, то есть ровно тогда, когда он
полезнее всего.

## Топология

```
                       repowise-caddy  :80  basic_auth        ← единственный публичный
                              │
                       repowise-web    repowise serve
                              │
   harness ──poh-harness-net──▶ repowise-proxy ──┬─▶ repowise-contour-mcp  :7338
   (аналитика, OpenHands)       журнал сессий    └─▶ repowise-product-mcp  :7338
                                                        │
                                repowise-indexer ───────┘  том repowise-workspaces
                                (расписание)               клоны + .repowise/wiki.db
```

## Спайки

| | что | почему |
|---|---|---|
| S1 | нужен ли `repowise login` для `serve`/`mcp`/`generate` | блокер: лицензия |
| S2 | ZAI как провайдер и чем эмбеддить | у ZAI может не быть эмбеддингов |
| S3 | SQLite WAL при одновременных записи и чтении | блокировки на живых запросах |
| S4 | формат MCP-конфига OpenHands | на нём стоит интеграция разработки |
| S5 | `.env` рабочих копий вне индекса | боевые ключи |
| S6 | диск под клоны с историей | на стенде ~23 ГБ |
| S7 | тарбол веб-UI ~50 МБ при первом старте | исходящий на стенде может быть закрыт |

S1 проверяется первым: от него зависит, возможна ли задача в принципе.

## Что осталось за рамками

- Выкладка в контур — третья задача, после решения по памяти сервера
- Вебхук вместо расписания — после того, как расписание себя покажет
- Repowise для PR-агента — он работает по диффу, постоянный индекс ему пока не нужен
