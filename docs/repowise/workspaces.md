# Правила структурирования по workspace

Workspace в Repowise — это **один корневой каталог с клонами, один репозиторий
по умолчанию и один MCP-эндпоинт**. Два workspace означают два контейнера на
разных портах. Отсюда все правила ниже: они про то, как поделить репозитории
организации так, чтобы ответы были точными, а эксплуатация — дешёвой.

Списки состава — `repowise/workspaces/contour.yml` и
`repowise/workspaces/product.yml`. Они ревьюятся как код.

## Два workspace и почему их два

| Workspace | Отвечает на вопрос | Кто спрашивает |
|---|---|---|
| `contour` | как устроены сами агенты | аналитика по задачам контура |
| `product` | что агенты пишут | аналитика и разработка целевых репозиториев |

Разделение обосновано **качеством ответов сейчас**, а не будущим ростом: вопрос
про целевой репозиторий не должен притягивать ответ про устройство агентов.
Цена — один контейнер и один файл конфигурации: механика индексации, прокси и
админки общая.

Возражение «преждевременно, в `product` всего один репозиторий» разбиралось на
дебатах и отклонено именно по этой причине — но оно разумное, и если шум в
ответах окажется меньше ожидаемого, объединение стоит дешевле разделения.

## Правила

**R1. Workspace — граница вопроса, не команды.** Не «репозитории команды А», а
«репозитории, про которые задают один и тот же класс вопросов».

**R2. Репозиторий живёт ровно в одном workspace.** Дубль означает два индекса
одного кода, разошедшихся во времени: агент получит два ответа и не поймёт,
какой свежий.

**R3. Alias равен имени репозитория на GitHub без владельца и не сокращается.**
`poh-issue-agents`, не `pia`. Alias уходит в каждый ответ MCP как указание на
источник и попадает в артефакт диалога — сокращение там потом не читается.

**R4. Первый в списке — репозиторий по умолчанию.** Запрос без alias падает на
него, поэтому первым ставится самый крупный и центральный: у `contour` это
`poh-issue-agents`, у `product` — текущая цель разработки.

**R5. Агент всегда адресует запрос alias'ом своего Issue.** Кросс-репозиторный
вопрос разрешён, но задаётся отдельным ходом и с явным указанием alias соседа —
в артефакте диалога это видно.

**R6. Порог включения: есть история git и больше 10 файлов.** Не включены по
этому правилу: `poh-pr-closer` (1 файл), `poh-po-task` (3),
`poh-security-agent` (2). Контекста они не несут, а шум в `list_repos` дают.

**R7. Добавить репозиторий = добавить строку в список состава.** Индексатор
склонирует его на ближайшем цикле, зарегистрирует в workspace и проиндексирует.
Ручных действий не требуется.

**R8. Общие исключения индексации фиксированы для всех:**

```
**/.venv/**   **/node_modules/**   **/__pycache__/**   **/.claude/worktrees/**
```

Последнее критично. В `poh-issue-agents` лежат рабочие копии его самого; без
исключения индекс кратно вырастет, а поиск начнёт возвращать устаревшие копии
как самостоятельные файлы — то есть уверенно отвечать про код, которого в
основной ветке нет.

**R9. Файлы окружения в индекс не попадают.** Индексатор **удаляет** `.env`,
`*.pem` и содержимое `secrets/` из рабочей копии перед индексацией — именно
удаляет, а не полагается на исключения: пакет сторонний, его дефолты меняются
между версиями, а ключ, попавший в индекс, оттуда уже не вынуть — он размажется
по страницам вики и по векторному индексу.

## Как решить, куда положить новый репозиторий

1. Про него будут спрашивать «как это устроено» в контексте работы агентов? →
   `contour`.
2. Агенты будут его **изменять**? → `product`.
3. И то и другое? Выбрать по преобладающему сценарию и записать выбор в
   комментарий в списке состава — R2 не даёт положить в оба.
4. Меньше 11 файлов или нет истории? Не включать вовсе (R6).

## Проверка после изменения списка

```bash
docker compose exec indexer python /app/indexer.py sync-once
docker compose exec repowise-contour-mcp repowise workspace list
```

Репозиторий должен появиться в выводе `workspace list`, а поиск по известному
символу — вернуть его файл. Если нет — [runbook.md](runbook.md).
