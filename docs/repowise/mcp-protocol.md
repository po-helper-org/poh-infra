# Протокол обращения к индексу

Единственный вход к индексу из контура — MCP-прокси. Прямое обращение к
MCP-эндпоинтам невозможно: их порты не публикуются и Traefik про них не знает.

## Точка входа

```
POST http://<прокси>:7400/mcp?workspace=<contour|product>&session=<id>
Authorization: Bearer <REPOWISE_AGENT_TOKEN>
Content-Type: application/json
Accept: application/json, text/event-stream
```

Тело — обычный JSON-RPC запрос MCP. Прокси передаёт его насквозь и не меняет.

### Обязательные параметры

| Параметр | Отсутствует → | Почему обязателен |
|---|---|---|
| `workspace` | `400` | прокси должен знать, к какому эндпоинту идти |
| `session` | `400` | артефакт рендерится из журнала; обмен без сессии восстановить нельзя |
| `Authorization` | `401` | второй рубеж после сетевой изоляции |

Пустой `REPOWISE_AGENT_TOKEN` в конфигурации прокси даёт `503`, а не открытый
доступ: за ним клоны всех репозиториев организации.

## Идентификатор сессии

Строится детерминированно (`shared/repowise.py` в `poh-issue-agents`):

```
rw-<agent>-<owner>__<repo>-<issue>
rw-analysis-po-helper-org__poh-demo-checkout-42
rw-openhands-po-helper-org__poh-demo-checkout-42
```

Детерминированно — чтобы повторный запуск по тому же Issue попадал в ту же
сессию, а не плодил осиротевшие журналы. Слэш заменён на `__`: идентификатор
уезжает в query-параметр, и кодировать его на каждой стороне незачем.

Аналитика и разработка по одному Issue — **две разные сессии**: это два разных
диалога, и слить их в один журнал значило бы потерять оба.

## Служебные точки

| Метод и путь | Токен | Что делает |
|---|---|---|
| `GET /health` | не нужен | живость прокси |
| `GET /index-age` | нужен | возраст индекса и SHA по каждому репозиторию |
| `GET /sessions/{id}/render` | нужен | транскрипт сессии в markdown |
| `POST /sessions/{id}/close` | нужен | зафиксировать завершение и отдать транскрипт |

`/health` открыт намеренно: проверка живости не должна падать из-за неверного
токена, иначе отличить «прокси лежит» от «токен протух» станет нельзя. Именно
на неё опирается ветвь деградации на стороне агента.

## Что прокси журналирует

Каждый вызов инструмента (`tools/call`) — время, имя инструмента, аргументы,
текст ответа, объём, длительность. Служебные методы (`initialize`,
`tools/list`, `ping` и подобные) в журнал не идут: это не диалог, а его
подготовка, и в артефакте они дали бы шум и сместили счётчик ходов.

Прокси **не разбирает семантику инструментов** — только конверт JSON-RPC. Имена
и сигнатуры инструментов у стороннего пакета меняются между версиями; привязка
к ним означала бы правку прокси на каждое обновление Repowise. Новый инструмент
в эндпоинте работает через прокси без единой правки.

## Инструменты индекса

Набор задаётся самим Repowise и зависит от версии. На `0.44.0` в режиме
workspace доступны, в частности: обзор репозитория, контекст по файлу или
символу, поиск по коду, объяснение решения, оценка риска правки, мёртвый код,
перечень репозиториев, путь зависимостей. Актуальный список — `tools/list` либо
веб-админка.

## Пример

```bash
curl -s -X POST "http://repowise-proxy:7400/mcp?workspace=product&session=rw-analysis-o__r-42" \
  -H "Authorization: Bearer $REPOWISE_AGENT_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call",
       "params":{"name":"get_overview","arguments":{}}}'

curl -s "http://repowise-proxy:7400/sessions/rw-analysis-o__r-42/render" \
  -H "Authorization: Bearer $REPOWISE_AGENT_TOKEN"
```

## Лимиты

| Что | Значение | Где задаётся |
|---|---|---|
| Ходов в диалоге | 12 | `REPOWISE_MAX_TURNS` у агента |
| Время обращения к эндпоинту | 120 с | `REPOWISE_UPSTREAM_TIMEOUT_SEC` |
| Проверка живости | 5 с | `PROBE_TIMEOUT_SEC` у агента |
| Хранение журналов | 30 суток | `REPOWISE_SESSION_TTL_DAYS` |

Потолок ходов обязателен: стадия аналитики живёт внутри активности Temporal с
потолком 900 секунд, и неограниченный цикл вопросов — это и расход средств, и
зависший прогон.
